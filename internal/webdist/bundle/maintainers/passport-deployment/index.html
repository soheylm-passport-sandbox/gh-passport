    Four-Repository Passport Deployment

    This runbook is for the IDEAL Lab IT administrator. Do not merge the handbook overhaul to main or invite learners until the production gates at the end are green.

    View exact sourceReturn to my dashboard

    This runbook is for the IDEAL Lab IT administrator. Do not merge the handbook overhaul to main or invite learners until the production gates at the end are green.

    The active 2026 deployment is declared in platform/deployment.json: IDEALLab/onboarding-IT remains the source, while the three exported runtime repositories use soheylm-passport-sandbox. Change that profile, regenerate the tracked deployment asset, and qualify every export before any future move. Until the overhaul PR is merged, handbook_ref deliberately names its reviewed feature branch so sandbox learners never land on obsolete main pages. Change it to main in the same reviewed change that makes main the deployed source.

    1. Export Deterministic Repositories#

    From a clean reviewed onboarding-IT commit:

    python3 scripts/export_exercises_repo.py /tmp/passport-exercises
python3 scripts/export_gh_passport.py /tmp/gh-passport
python3 scripts/export_onboarding_control.py /tmp/onboarding-control
python3 scripts/render_deployment_assets.py --check

    Diff each export against its target before pushing. The exercises and extension repositories are public. onboarding-control remains private.

    2. Protect The Public Exercise Repository#

    main accepts changes only through reviewed PRs. Disable force pushes and deletions, require conversation resolution, and require the controller check once its production App is active. Public learner forks contain no organization secrets and no privileged workflow.

    Add the gh-extension topic to gh-passport. Keep passport-exercises deliberately small: fictional fixtures, empty evidence, generated fallback missions, and non-secret metadata only.

    3. Configure The Controller App#

    Create one GitHub App and install it only on soheylm-passport-sandbox/passport-exercises.

    Minimum permissions:

    Permission Exercises
    Metadata read
    Contents read
    Checks read/write
    Issues read/write
    Pull requests read/write

    Store the public App client ID as repository variable CONTROLLER_APP_CLIENT_ID and the private key as CONTROLLER_APP_PRIVATE_KEY only in the private control repository. The client ID mints installation tokens; the immutable numeric App ID comes only from the reviewed deployment profile and verifies that Check Runs came from the expected App. The control repository's own GITHUB_TOKEN writes bounded assignment and registry commits. The public launcher compiles the numeric App ID from the reviewed deployment profile. It never receives the private key. The release workflow has no App credential and no independently configurable App identity.

    The App never writes to personal forks and no secret reaches an untrusted checkout or container.

    4. Lock Automation Cost Before Enabling It#

    The controller uses grouped scheduled polling because a GitHub App webhook requires an always-on, lab-owned HTTPS endpoint. Do not use an unaudited webhook relay or a privileged public pull-request workflow as a shortcut.

    The default cadence is every 30 minutes during weekday daytime and every three hours otherwise. GitHub cron is UTC. One unchanged discovery normally consumes one rounded private Actions minute; each changed PR adds one serial assessment job. Workflow-level concurrency prevents overlapping controller runs, and job timeouts bound stalled consumption.

    GitHub documents scheduled events as best-effort: they may be delayed and, at high load, dropped. Do not mark the scheduled-assessment production gate as complete from YAML inspection or a manual dispatch. Observe at least one live schedule event on the default branch and retain workflow_dispatch as the recovery path.

    Before enabling the schedule, open the sandbox organization's Settings > Billing and licensing > Budgets and alerts and apply one of these hard stops:

    1. For the zero-cost pilot, confirm that GitHub reports no payment method. Do not add one: usage stops after the included allowance.
    2. If the organization later has a payment method, create a product-level GitHub Actions budget and enable Stop usage when budget limit is reached. An email alert alone does not prevent charges.

    Keep included-usage alerts enabled. Recheck usage after the first five learners and after the first full cohort. Never enable larger runners for this workflow.

    A future event-driven webhook may replace frequent polling only after its receiver verifies GitHub's signature before parsing the event, accepts only pull-request events from the exact exercise repository, deduplicates delivery IDs, dispatches the private controller without exposing its token, and has an owned monitoring and recovery path.

    5. Publish A Launcher Release#

    The gh-passport release workflow tests Windows, macOS, and Linux, then emits GitHub CLI's documented asset names:

    gh-passport-windows-amd64.exe
gh-passport-darwin-amd64
gh-passport-darwin-arm64
gh-passport-linux-amd64
gh-passport-linux-arm64

    Create and push a reviewed semantic tag such as v0.2.0. The workflow builds the reviewed App identity embedded by the deployment profile. Verify a clean installation on each claimed platform:

    gh extension install soheylm-passport-sandbox/gh-passport
gh passport version

    Do not teach learners to bypass Gatekeeper, SmartScreen, antivirus, or global execution policy.

    6. Enroll Learners Asynchronously#

    Use Enroll one learner for an individual or Enroll a learner cohort for one-per-line or comma-separated usernames. Cohort input is limited to 100 and the complete request is validated before any file is written. Supply only GitHub usernames, one reviewer username, and an optional due date. The private workflow updates operations/cohort-status.md; this view is convenient but Check Runs and registry records remain authoritative. No operating system, answers, credentials, or research context belongs there.

    As that learner:

    gh auth login --web --git-protocol https
gh extension install soheylm-passport-sandbox/gh-passport
gh passport start

    The scheduled control workflow must automatically:

    1. find exactly one central draft PR;
    2. verify author ID, fork ID/parent, source/base, branch, and route;
    3. freeze a private assignment and trusted manifest;
    4. check the exact public fork SHA without credentials or network;
    5. publish one Check Run and one upserted PR comment;
    6. request the assigned reviewer only when deterministic gates pass;
    7. append a minimal completion record after exact-SHA approval.

    7. Failure And Recovery Tests#

    Prove all of these before learners are invited:

    • rerunning gh passport start reuses the fork, branch, PR, and route;
    • a wrong existing directory or remote stops without mutation;
    • a closed unmerged PR is replaced by rerunning gh passport start, without a replacement branch or route; a merged PR stops for private help;
    • a forged fork, username, route, Check Run name, App ID, or stale approval is rejected;
    • a possible secret stops before execution and before optional AI transmission;
    • unselected or protected paths fail the editable allowlist;
    • an interrupted controller run is retried idempotently;
    • two authority updates persist without force-pushing or losing either record;
    • deleting .passport-local/ loses navigation only and sync restores official status;
    • the public preview never claims assignment or completion state.

    8. Learner Cutover#

    Only after qualification:

    1. merge the reviewed onboarding branch to main;
    2. send learners the GitHub-rendered README first-contact link;
    3. enroll identities and reviewers asynchronously;
    4. monitor scheduled failures, rate limits, PRs without trusted checks, stale review requests, and registry persistence;
    5. keep the Markdown workbook as the no-JavaScript fallback, not a second curriculum.

    Rollback pins a previously reviewed matching curriculum, launcher, exercises, and controller release. It never deletes public evidence or private completion history.

    Production Gates#

    • passport-exercises is public and protected.
    • gh-passport is public, tagged, and installable on clean machines.
    • onboarding-control is private with App variable/key configured.
    • Paid Actions overage is impossible and included-usage alerts are enabled.
    • Scheduled registration and exact-SHA assessment succeeded live in the sandbox on 2026-09-02.
    • One synthetic non-admin learner completes the public-PR loop.
    • Windows, macOS, and Linux launcher journeys pass.
    • No privileged key appears in a public repository, workflow, artifact, or log.
    • The overhaul PR is reviewed; it is not self-merged during deployment work.
