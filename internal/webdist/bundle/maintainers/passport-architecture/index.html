    Passport System Architecture

    The product is a local-first browser application backed by public GitHub pull requests and a private controller. The lab does not operate a permanent learner web service, OAuth callback, analytics service, or student database.

    View exact sourceReturn to my dashboard

    The product is a local-first browser application backed by public GitHub pull requests and a private controller. The lab does not operate a permanent learner web service, OAuth callback, analytics service, or student database.

    Repository Boundaries#

    IDEALLab/onboarding-IT          handbook, curriculum, site, exporters
soheylm-passport-sandbox/passport-exercises    public, privilege-free exercises and PRs
soheylm-passport-sandbox/gh-passport           public precompiled launcher releases
soheylm-passport-sandbox/onboarding-control    private enrollments, controller, operations, registry
username/passport-exercises    learner-owned public fork

    platform/deployment.json is the single active deployment identity. The handbook source deliberately remains under IDEALLab; the three operational repositories deliberately share soheylm-passport-sandbox for the 2026 semester. Students are not members of either organization.

    Operations, controller, assignment state, and registry are logical subsystems inside one private repository. Separate GitHub App identities may still be used if the permission audit requires them; repository count is not a security boundary.

    Learner Journey#

    GitHub-rendered first contact
  -> install Git and GitHub CLI
  -> gh auth login
  -> gh extension install soheylm-passport-sandbox/gh-passport
  -> gh passport start
       -> create/reuse personal public fork
       -> verify origin and official upstream
       -> select responsibilities and resolve dependencies
       -> create/reuse onboarding/<username>
       -> write passport.json and push
       -> create/reuse one central draft PR
       -> launch 127.0.0.1:<random-port>
  -> complete one mission and push
  -> scheduled private controller assesses exact PR SHA
  -> final reviewer requested automatically
  -> minimal private completion record

    The launcher refuses an ambiguous existing directory, unexpected remote, wrong branch, incompatible curriculum, changed route, or untrusted controller identity. It never force-pushes, deletes, merges, or rewrites an existing route.

    State And Authority#

    State Location Meaning Authority
    Last opened mission gitignored .passport-local/state.json Convenience on one clone None
    Uncommitted evidence Local worktree Draft None
    Pushed fork commit Public fork Submitted source Audit only
    Permanent central draft PR Public exercises repository Feedback and review thread Audit only
    Controller Check Run Central repo, trusted App ID, exact SHA Objective status Deterministic authority
    Authorized review Central PR, reviewer ID, exact SHA Open-ended judgment Human authority
    Completion record Private control registry Minimal endorsement Final record
    Cohort status view Private operations/cohort-status.md Derived asynchronous overview None; convenience only

    The learner-controlled passport.json proposes a route only at registration. The private assignment freezes immutable GitHub IDs, fork ancestry, base repo, PR number, branch, curriculum, platform, responsibilities, missions, baseline, reviewer, and a protected hash of passport.json. Later learner changes cannot alter authority.

    Trust Checks#

    Registration requires all of:

    1. an active private enrollment;
    2. one open PR into soheylm-passport-sandbox/passport-exercises:main;
    3. PR author ID equal to the enrolled learner ID;
    4. head repository equal to the learner's public fork;
    5. fork ID and direct parent equal to the official exercises repository;
    6. onboarding/<lowercase-username>;
    7. schema-v2 passport identity matching origin/source/fork;
    8. a route exactly resolved by the pinned curriculum.

    Assessment revalidates the PR and SHA before and after isolated execution. Secret scanning happens before parsing or execution. Untrusted behavior runs in a read-only, network-disabled, bounded container without credentials. The App is installed only on the central exercise repository with read-only Contents and write access to Checks, Issues, and Pull requests. The private control workflow uses its own GITHUB_TOKEN for bounded commits inside onboarding-control. Neither credential can write to a learner fork.

    If the learner closes an unmerged assessment PR, rerunning gh passport start creates another draft PR. Registration rotates the trusted PR number only after revalidating the same identity, fork, route, and frozen passport.json. A merged PR is never repaired automatically.

    Local Web App#

    The precompiled Go extension binds only to IPv4 loopback on a random port and serves embedded, compiler-sanitized Astro assets. Browser requests cannot supply shell commands or arbitrary GitHub URLs. HttpOnly SameSite cookies, exact Host/Origin checks, CSP, no-store, body limits, and strict JSON contracts protect the bridge. The GitHub token remains inside gh.

    Closing the browser or terminal loses no GitHub work. Reopening with gh passport open restores local navigation; gh passport sync reconstructs official status from the permanent PR and trusted Check Run.

    Privacy And Public PRs#

    Public PRs are an explicit constraint. Exercises therefore use fictional values and short sanitized evidence only. Real incidents, account information, research data, broad logs, and confidential details are forbidden. Private control state stores numeric identities, SHA/status projections, route IDs, and minimal completion facts, not exercise bodies or analytics.

    Versioning#

    Curriculum and launcher use semantic versions. A launcher release embeds one curriculum version and immutable controller App ID. Dirty source builds are development previews and cannot claim exact-source provenance or be released.
